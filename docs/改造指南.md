# 从 OpsPilot Zero Demo 改造为「报销无忧」产品指南

> 依据:[《方案.md》](方案.md)(5 Agent + 8 步闭环 + Skill 九项)+ 2026 GOAI 官方赛题必选/推荐项(赛题原文未随本仓库分发)
> 原则:官方 Demo 是**配置驱动**,改造 = 换"皮"(内容)不换"骨架"(结构),全程不需要改 Python 框架代码。

---

## 0. 为什么这个 Demo 特别好改(先说结论)

| Demo 组成部分 | 形式 | 改造方式 |
|---|---|---|
| Agent | `agents/*/Agent.md`(评审用)+ `at/create_agents_messages.md` 内联 AgentSpec(运行时用) | **改 Markdown 内容** |
| Skill | `skills/*/SKILL.md`(frontmatter + Purpose/Inputs/Procedure/Output Contract/Quality Gates) | **改 Markdown 内容** |
| Team 编排 | `at/team_spec.json`(创建顺序 + workflow + risk_policy) | **改 JSON** |
| 工具 | `tools/mock_tool_server.py` + `tools/tool_catalog.json`(含 `future_mcp_mapping`) | **替换 mock 工具函数 + 改 JSON 目录** |
| 场景输入 | `scenarios/*.json` | **换成报销场景数据** |
| AgentTeams 运行 | 装好后在 Element Web 的 `manager` 房间发创建消息,在 Team 房间发任务 | **复用同一套流程,内容换成报销任务** |

> 关键认知:运行时 Worker **不读宿主机文件**,`agents/`、`skills/` 下的 Markdown 是给评审追溯和后续 Nacos Registry 用的;真正生效的是内联在创建消息里的 AgentSpec。所以两边都要改,但结构完全一致。

## 3. AgentTeams 功能如何"同步"到产品里(第二个问题的答案)

AgentTeams 装好后提供以下能力,改造后的产品要**逐项用到并在方案中说明映射**(这正是赛题 12.2-① 核验点):

| AgentTeams 能力 | 落地到报销产品的具体操作 | 对应赛题/方案 |
|---|---|---|
| **Manager 编排** | 在 `manager` 房间发创建消息:串行创建 5 个业务 Worker,再让 manager 创建独立 TeamLeader Worker `reimburse-zero-demo-leader` | 方案 §3.3 角色编排 |
| **任务拆解** | TeamLeader 收到报销任务后按 workflow 依次派给 Intake → 稽核 → 评级 → 处置 → 复盘;workflow 写在 `team_spec.json` | 方案 §3.3 任务拆解 |
| **上下文传递** | Team 房间消息承载单据对象与中间结论;每个 Worker 的输出 contract 就是给下一个 Worker 的输入(官方 demo 即如此,报销版保持) | 方案 §3.3 上下文传递 |
| **协同执行** | 高风险分支:处置 Agent 只生成审批任务(`mock_approval.create_approval_task`),审批通过后人工/模拟确认再执行支付 | 方案 §4 第 7 步 |
| **状态追踪** | AgentTeams 的 Matrix 会话天然留存全部消息(角色→时间→结论),即执行轨迹;导出聊天记录 + mock 网关日志作为 Trace/Log 证据 | 方案 §8 可观测 |
| **风险策略** | `team_spec.json` 的 `risk_policy`:`auto_execute: ["L0","L1"]`(低风险自动放行),`approval_only: ["L2","L3"]`(超限/打款必须审批)——**打款动作必须放进 approval_only** | 方案 §9.2 合规红线 |

> 结论:AgentTeams 不是"要另外开发的功能",它是**已经安装好的运行时**;所谓"同步"= 把你方案里的 5 Agent / 8 步闭环 / 审批回滚,**用 AgentTeams 的消息创建、Team 编排、risk_policy 原样实现一遍**,并在 PPT 里用"我们这样映射到框架能力"讲清楚。

## 4. 工具改造(报销版 mock 工具清单)

官方 `mock_tools.py` 有 8 个工具;报销版建议替换为:

| mock 工具 | 函数 | 用途 | future_mcp_mapping |
|---|---|---|---|
| `mock_invoice` | `verify` | 发票真伪与要素核验(返回真/伪/要素一致) | `tax.invoice_verify` |
| `mock_policy` | `search` | 报销政策条款检索(职级/费用类型/限额) | `knowledge.policy_rag` |
| `mock_claim` | `get_claim`, `list_history` | 报销单详情、历史单据(供查重) | `finance.claim_query` |
| `mock_payment` | `execute`, `rollback` | 支付执行(幂等键)、失败回滚 | `payment.gateway` |
| `mock_approval` | `create_approval_task`, `resolve` | 生成人工审批任务、模拟审批结果 | `workflow.approval` |
| `mock_ledger` | `post_entry`, `verify_entry` | 入账、入账验证 | `finance.ledger` |

`tool_catalog.json` 同步替换,每个工具保留 `kind: http-mock-adapter` 与 `future_mcp_mapping`,证明"后续只包一层 MCP Server 即可接入真实系统"(赛题 9.2 迁移成本)。

## 5. 从零到跑通:10 步操作顺序

1. **准备骨架**:使用本仓库的 `demo/`(已由官方 OpsPilot Zero Demo 改造完成);如需从官方原始包重做,把赛事方提供的 `opspilot-zero-demo.zip` 解压到工作区并改名为 `demo/`。
2. **scenarios 先行**(先有输入才能验证):按《方案.md》附录 C 造 2-3 笔模拟报销(正常/超标/重复或假票),写成 `scenarios/*.json`。
3. **改 tools**:在 `mock_tools.py` 里实现 §4 的 6 个报销 mock 工具(沿用现有 `SCENARIO_DATA` + 函数映射模式);更新 `tool_catalog.json` 与 `MCP_MAPPING.md`。
4. **写 SKILL.md**:新增 `invoice-verify`、`duplicate-check`、`audit-report`,改写其余 7 个为报销语义(§2 清单)。
5. **写 Agent.md**:5 个 Agent 各写 Mission/Inputs/Skills/Tools/Output Contract(输出 JSON 与场景字段对齐)。
6. **改创建消息**:把 `at/create_agents_messages.md` 的 4 Worker 内联 AgentSpec 换成 5 Worker 报销版(mission 用中文、tool contracts 指向报销 mock 工具、输出 contract 用报销字段)。
7. **改 team_spec + 任务消息**:`team_spec.json` 的 creation_policy.order = `[intake, audit_analyst, risk_rater, executor, reviewer, team]`,workflow 6 步换成报销 8 步(可合并为 6 个 step),risk_policy 把打款放进 approval_only;`run_demo_task_message.md` 换成报销任务文案。
8. **运行**:按 [AgentTeams 运行手册](../demo/at/AGENTTEAMS_RUNBOOK.md) 安装 AgentTeams(或复用已装环境);启动 `python3 demo/tools/mock_tool_server.py --port 18089`;按 RUNBOOK 找到容器可达地址;把创建消息发给 `manager`;进 Team 房间 `@leader` 发第 1 笔报销任务。
9. **验证**:对照 §6 验收清单看最终报告是否含 8 步证据、审批节点、回滚逻辑。
10. **收集证据**:导出 Element 聊天记录 + mock 网关日志 + 报告截图 → 进 PPT §9/§12 作为运行证据。

## 7. 注意事项

1. **运行时只认内联 AgentSpec**:`agents/*.md` 改得再好,也必须同步改 `at/create_agents_messages.md` 里的内联版本,否则运行时不生效。
2. **审批是"只生成审批计划"而非"自动执行"**:官方 demo 的 L2/L3 机制直接复用为打款审批,不要改成自动打款——这是合规红线也是得分点。
3. **mock 政策库 ≠ 真 RAG**:初赛 mock 足够;文档里声明"复赛用向量库 + PolarDB 实现知识库 RAG"。
4. **Worker 命名避免与官方冲突**:Team/TeamLeader 名字改成 `reimburse-zero-demo` / `reimburse-zero-demo-leader`,防止与旧 Team 混淆。
5. **一次只发一笔报销任务**:沿用官方"逐条发送、等报告完成再发下一条",避免并发上下文互相干扰。
